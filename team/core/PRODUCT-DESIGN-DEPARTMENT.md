# PRODUCT-DESIGN-DEPARTMENT.md — экспериментальный отдел проектирования

Статус: **эксперимент до решения владельца Dream Team после пилота**.

Отдел получает сырой замысел вплоть до одной фразы и самостоятельно проектирует
целостный образ продукта. Его единственный пользовательский результат — понятная
**Product Map**. Ключевые записи остаются на карте, а все подробности, варианты,
источники и промежуточные наработки сохраняются в связанных файлах.

После показа карты отдел ждёт решения владельца. Никакой следующий процесс не
запускается автоматически.

## 1. Главное правило

Владелец не обязан заранее назвать ядро, области или полный функционал. Отдел:

1. сам предлагает первый контур продукта;
2. показывает, что считает ядром и почему;
3. по существенным развилкам приносит 2–3 варианта, последствия и рекомендацию;
4. спрашивает владельца, какой вариант ближе;
5. сохраняет ответ и продолжает проектирование.

Вопрос без собственной проектировочной версии — не результат работы отдела.

## 2. Состав первого эксперимента

- **`product-architect`** — проектирует продукт, ведёт Product Map и подробные файлы.
- **`product-design-reviewer`** — независимо и read-only проверяет весь пакет.
- **Владелец** — выбирает только существенные развилки и решает, что делать с
  готовой картой после показа.
- **Оркестратор** — держит маршрут, файлы, независимость и фиксацию решений,
  но не проектирует продукт вместо профессиональной роли.

Product Owner, Business Analyst доставки, Design, Build и QA в отдел не входят.

## 3. Маршрут

```text
сырой замысел
  → product-architect предлагает контур, ядро и области
  → при существенной развилке: варианты + последствия + рекомендация → владелец
  → product-architect ведёт Product Map и подробные файлы параллельно
  → оркестратор фиксирует commit кандидата
  → product-design-reviewer проверяет именно этот commit
  → при замечаниях: product-architect исправляет их → новый commit → новое ревью
  → PASS и ссылка на проверенный commit фиксируются внутренним отчётом
  → машинная проверка подтверждает неизменность карты после ревью
  → карта показывается владельцу
  → ОЖИДАНИЕ РЕШЕНИЯ ВЛАДЕЛЬЦА
```

Ответ владельца на готовую карту закрывает текущий прогон. Просьба о правках
записывается как вход нового прогона; новая итерация не начинается сама.

## 4. Когда спрашивать владельца

Спрашивать только когда выбор меняет:

- назначение или аудиторию продукта;
- состав ядра;
- ключевой пользовательский путь;
- границы продукта или важную сущность;
- необратимое ограничение.

Формат вопроса:

| Вариант | Что получится | Плюсы | Ограничения |
|---|---|---|---|
| A |  |  |  |
| B |  |  |  |

Затем: **рекомендация отдела** и один вопрос «какой вариант выбираем?». Ответ
сохраняется дословно в `DECISIONS.md`.

Обратимые детали архитектор решает сам как помеченные гипотезы.

## 5. Рабочий контур

```text
docs/product-design/<run-id>/
  MANIFEST.md
  PRODUCT-MAP.md
  SOURCE-REGISTER.md
  DECISIONS.md
  TRACEABILITY.md
  nodes/
    NODE-001-<slug>.md
  reviews/
    <iteration>.md
```

Документ этапа не создаётся заранее: его наличие означает выполненную работу.

### Что находится на карте

- короткий образ продукта;
- области и возможности ядра;
- общий пользовательский путь;
- ключевые решения и ограничения;
- открытые вопросы и непокрытые области;
- ссылка `Подробности` на каждый проектировочный файл.

### Что остаётся в файлах

- полный разбор каждого узла по пяти ракурсам;
- источники и точные координаты;
- варианты, рекомендации и ответы владельца;
- гипотезы, отброшенные варианты и причины;
- служебная трассировка карты к наработкам.

Служебные ID не показываются на основной карте. В Google Sheets карта и
трассировка живут на разных вкладках. Канонический версионируемый снимок всегда
сохраняется в `PRODUCT-MAP.md`; Google Sheet допустима только как дополнительное
представление, если все ссылки `Подробности` реально открываются у владельца.

Отчёт reviewer остаётся внутренним входом для архитектора и оркестратора. При
передаче рядом с Product Map виден только статус проверки. Отдельно владельцу
отчёт не передаётся, если в нём нет вопроса, который действительно требует
решения владельца.

## 6. Статусы

Каждое утверждение в подробных файлах имеет статус:

- `факт` — точный источник;
- `интерпретация` — вывод из названных источников;
- `гипотеза` — рабочее предложение;
- `открытый вопрос` — требуется решение.

## 7. Гейт готовности Product Map

- отдел начал с сырого замысла и сам предложил контур;
- карта показывает целый продукт, а не список случайных функций;
- ядро и граница покрытия названы честно;
- ключевые записи читаются без кодов и перехода в детали;
- каждая область ведёт к связанному файлу;
- источники, решения и карта согласованы через `TRACEABILITY.md`;
- существенные развилки имеют варианты и решение либо открытый статус;
- reviewer поставил `PASS`;
- актуальный reviewer-отчёт ссылается на конкретный commit кандидата;
- содержимое карты и подробных файлов не менялось после этого ревью;
- итоговый пакет с отчётом зафиксирован commit-ом до показа владельцу;
- машинная проверка подтверждает, что показанный пакет совпадает с этим commit;
- после показа ничего не запускается автоматически.

## 8. Успех пилота

- новый чат начинает только с фразы «мне нужна канбан-доска»;
- отдел сам предлагает ядро и области, не просит владельца составить их;
- владелец отвечает только на содержательные варианты;
- итоговая карта понятна без чтения служебных файлов;
- по ссылкам можно восстановить все наработки и источники;
- после показа карты отдел ждёт решения владельца.
