# Иллюстрации — контракт передачи (design-lead → graphic-designer)

Стык между тем, кто РЕШАЕТ, где нужна графика (`design-lead`), и тем, кто её ДЕЛАЕТ
(`graphic-designer`). Без этого контракта иллюстратор не знает, что от него хотят, и начинает выдумывать.

## Карта иллюстраций (владелец — design-lead)
Артефакт проекта `docs/illustrations/map.md`. На каждый слот:
- **место** — экран + позиция (и метка-плейсхолдер в макете/коде);
- **тип** — hero / empty-state / promo / иконка-акцент / 404 …;
- **контекст и эмоциональный тон** — что происходит, что должен почувствовать юзер;
- **что НЕ надо** — явные анти-паттерны стиля;
- **референс** — ссылка/файл образца стиля и/или содержания (**ОБЯЗАТЕЛЬНО**);
- **приоритет** и **статус** (нужен / в работе / принят).

## Слот в макете
`design-lead` помечает в макете/коде **место под иллюстрацию** (плейсхолдер + id слота из карты),
чтобы фронт оставил «дырку» под арт, а не придумал что-нибудь своё.

## Источник референсов
Каждый слот идёт **с референсом** — иначе `graphic-designer` не поймёт, чего хотят. Откуда берём
референсы — **решение проекта** (стейкхолдер даёт / design-lead собирает / каталог), фиксируется в
`PROJECT.md`. Нет референса → `graphic-designer` не начинает, идёт к `design-lead`.

## Поток
1. `design-lead` заполняет слот в карте: контекст + тон + что-не-надо + **референс**.
2. `graphic-designer` генерит по слоту, итерирует до попадания в стиль.
3. **`design-lead` принимает** визуал слота.
4. **Стейкхолдер** решает, какие слоты берём и бюджет генерации.
5. `frontend`/`tech-lead` интегрирует принятое.

## Правило
`graphic-designer` НЕ начинает слот без **контекста + референса**. Нет — к `design-lead`, не выдумывает.
