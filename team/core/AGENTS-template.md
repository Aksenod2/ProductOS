## Порядок работы (local-verify → push)

1. Делаем изменение.
2. Проверяем локально; при UI-правках — скриншоты mobile + desktop.
3. Показываем результат стейкхолдеру (на уровне доверия СТРОГИЙ) / фиксируем в журнале.
4. Только после этого — коммит и push. Не пушим непроверенное. {{ветка прода}} = прод.

## ⚑ Гейт перед пушем: полный BUILD, а не только тесты (ОБЯЗАТЕЛЬНО)

Перед КАЖДЫМ пушем в прод-ветку гоняем ИМЕННО прод-сборку (ту же команду, что
собирает хостинг/CI): {{команда прод-сборки}}.

Почему мало юнит-тестов и «лёгкого» тайпчека: тест-раннеры на esbuild/swc не
делают типизацию вообще; `tsc --noEmit` может не включать часть файлов, а
прод-сборка строже. **«Зелёные юнит-тесты ≠ билд пройдёт».** Гейт автоматизирован
проектным гейтом `{{BUILD_GATE_SCRIPT}}` — push в прод-ветку без свежей
сборки блокируется.

При изменении ОБЩЕГО типа/контракта — грепнуть ВСЕ места использования
(литералы, моки, тест-утилиты) и обновить в том же коммите.

## ⚑ Спека → реализация (ОБЯЗАТЕЛЬНО)

**Новая фича ИЛИ меняется поведение** → сначала согласованная спека, потом код.
Цепочка с воротами утверждения стейкхолдером: бизнес-аналитик (что умеет фича,
граничные случаи, открытые вопросы с вариантами) → системный аналитик (контракт:
эндпоинты, правила, права) → дизайн (экраны и состояния) → реализация.

**Косметика / мелкий фикс** (поведение не меняется) → делаем сразу, без парада
ролей. Не топить мелочь в процессе.

## ⚑ Журнал работ для стейкхолдера (ОБЯЗАТЕЛЬНО)

Каждый блок работ из области, невидимой стейкхолдеру ({{например: бэкенд, инфра}}),
завершается записью в `docs/journal/{{область}}.md` простым языком:
**что изменилось** (в терминах продукта) / **как проверили** (поведением, не
«тесты зелёные») / **что это значит для стейкхолдера**. Свежие сверху.
Работа без понятного стейкхолдеру доказательства поведения = не принята.
