# MODEL-ROUTING.md — канон выбора модели и вызова субагентов

Цель правила — тратить сильную модель там, где нужна профессиональная ответственность,
и не оплачивать её глубину для механической работы. Модель выбирается по риску и
неоднозначности конкретного узла, а не по тому, что исполнитель называется субагентом.

Точные названия моделей не входят в переносимый канон. Их задаёт тонкий адаптер среды.
Мастер-роли сохраняют `model: inherit`: роль определяет профессию, этот файл — требуемый
уровень, адаптер — доступную модель.

## 1. Сначала решить, нужен ли субагент

Субагент запускается, только если работа:

- является отдельным ограниченным узлом с понятным результатом;
- может идти независимо или должна вынести шумный поиск/логи из основной сессии;
- выигрывает от отдельной профессиональной проверки.

Один короткий неделимый шаг оркестратор делает сам. Нельзя создавать несколько агентов
для одного и того же вопроса «на всякий случай» без явной причины сравнивать ответы.

Автоматический fan-out (например, Ultra в Codex) — режим параллелизма, а не уровень
качества. Он включается только для двух и более действительно независимых веток.

## 2. Три уровня

### lead — сильная модель

Использовать для неоднозначного, критичного и объединяющего:

- оркестрация и финальный синтез;
- продуктовый замысел и решения владельца;
- архитектура, безопасность, данные, деньги и необратимые действия;
- дизайн-направление без однозначного правила;
- независимый критичный verdict и релизная приёмка;
- конфликтующие источники или последствия сразу для нескольких подсистем.

Критичный проверяющий остаётся независимым и read-only, если это требует его роль.

### standard — сбалансированная модель

Использовать для обычной работы с ясными входами и критериями:

- ограниченная реализация по принятой спеке;
- аналитика с заданной рамкой;
- документация и тесты по известному контракту;
- исправление локального дефекта после установленной причины;
- штатная входная проверка артефакта без красных флагов.

### mechanical — экономная модель

Использовать для повторяемой read-heavy работы:

- поиск файлов и фактов, инвентаризация, извлечение;
- разбор логов по заданным признакам;
- запуск готовых проверок и сбор их результатов;
- форматирование, классификация и структурированное резюме;
- сверка по полностью механическому чек-листу.

`mechanical` не принимает продуктовые решения и не ставит финальный блокирующий verdict.

## 3. Обязательная эскалация

Исполнитель `mechanical` или `standard` останавливается и возвращает
`escalation_needed: true`, если:

- затронуты безопасность, данные, деньги, релиз или необратимое действие;
- требуется решение владельца или замысел допускает несколько трактовок;
- источники противоречат друг другу или доказательств недостаточно;
- задача второй раз вернулась с той же причиной;
- меняется сквозная архитектура или несколько подсистем;
- требуется отрицательный или спорный профессиональный verdict.

Оркестратор после этого передаёт узел на `lead`, а не просит экономную модель угадать ещё раз.
Один повтор на том же уровне допустим только для исправления явной технической ошибки.

## 4. Бюджет делегирования

- Глубина по умолчанию — один уровень: субагенты не создают субагентов.
- Запускается минимальное число агентов, необходимое для независимых узлов.
- В контекст передаются цель, scope, входы, нужные пути, ограничения и контракт выхода,
  а не вся история основной сессии.
- Субагент возвращает вывод и доказательства; сырые логи остаются в артефакте или файле.
- Параллельные пишущие агенты соблюдают worktree и hot-zone правила инженерного канона.

## 5. Контракт runtime

До запуска оркестратор фиксирует:

- мастер-роль и конкретную задачу;
- запрошенный уровень: `lead`, `standard` или `mechanical`;
- причину выбора и ожидаемый результат;
- условия эскалации.

После запуска фиксируются фактическая модель/усилие, verdict и эскалации. Если среда не
умеет выбрать запрошенную модель, это помечается как `runtime_override_unavailable`;
наследованная модель используется безопасно, но экономия не считается доказанной.

Для полной дорожки эти данные входят в `MANIFEST.md` и дневной журнал. На лёгкой дорожке
достаточно короткой записи оркестратора.

## 6. Адаптер запуска в Codex

Переносимый приоритет способов запуска:

1. Нативный отдельный thread с явными полями модели и reasoning effort — основной путь,
   когда требуется гарантировать экономный или критичный runtime.
2. Универсальный `spawn_agent` без селектора модели используется только тогда, когда
   наследование runtime оркестратора допустимо. Название роли или задачи само по себе не
   доказывает, что была выбрана другая модель.
3. Отдельный CLI-процесс с явными model/effort/sandbox — headless fallback, если нативный
   thread недоступен.
4. Терминал внешнего оркестратора — путь для долгих наблюдаемых DAG-задач, но не для
   одного короткого механического чтения.

До передачи логов и больших корпусов оркестратор детерминированно сужает вход: даты,
точные пути, нужные диапазоны и признаки поиска. Экономная модель на широком неотфильтрованном
контексте не считается экономным запуском.

После старта оркестратор проверяет и сообщает фактические модель, effort и sandbox. Если
это нельзя подтвердить, применяется `runtime_override_unavailable`; роль не выдаётся за
доказательство выбора runtime.
