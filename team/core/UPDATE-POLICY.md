# UPDATE-POLICY — обновление мастер-команды без потери истории

Dream Team обновляется централизованно, но правила уже идущей задачи не должны меняться
незаметно. Версия команды является частью происхождения каждого эпика.

## Где публикуются изменения

- `VERSION` — текущая версия мастер-команды;
- `CHANGELOG.md` — человеческое описание изменений и совместимости;
- Git-тег `vX.Y.Z` — неизменяемая точка версии;
- GitHub Release — уведомление пользователям и инструкция обновления;
- `team/HISTORY.md` — история взросления и причины решений, не замена release notes.

## Что фиксирует проект

В корневом `AGENTS.md` проекта записываются путь к мастер-команде и выбранная версия.
При создании эпика в `MANIFEST.md` обязательно фиксируются:

- версия Dream Team;
- commit мастер-репозитория;
- дата старта эпика.

Дневная запись сохраняет `role_id` и версию мастер-команды, фактически загруженную в этом
запуске. Поэтому по истории можно восстановить не только имя роли, но и конкретные правила,
по которым она работала.

## Обновление между эпиками

Между эпиками пользователь обновляет клон ProductOS и читает `CHANGELOG.md`. Новый эпик
закрепляет новую версию. Проектный контур не перезаписывается: новые обязательные файлы или
поля добавляются как явная миграция после инвентаризации.

## Обновление во время эпика

По умолчанию активный эпик завершается на закреплённой версии. Срочное обновление посреди
эпика допускается только отдельным решением владельца проекта. Тогда оркестратор:

1. записывает старую и новую версии, причину и источник решения в дневной журнал;
2. обновляет версию в `MANIFEST.md`;
3. повторно валидирует все ещё открытые контракты стыков;
4. фиксирует изменившиеся требования, гейты и следующий безопасный шаг.

Без этой записи смешивать версии внутри эпика запрещено.

## Совместимость

- PATCH можно применять между задачами без миграции, если `CHANGELOG.md` не говорит обратное;
- MINOR требует прочитать новые возможности и проверить проектные адаптеры;
- MAJOR требует явной миграции по инструкции релиза.
