# PRODUCT-MAP-USM-SHEETS-STANDARD.md — стандарт Google Sheets v4

Статус: **утверждённый канон Dream Team**. Версия: **v4**.

Мастер-шаблон: доступную ссылку на Product Map + USM v4 предоставляет владелец
в контексте проекта. Личная таблица автора в публичный пакет не входит.
Если шаблон или Google Sheets недоступны, применяется Markdown-режим из §1;
не создавайте таблицу с выдуманной структурой и не заявляйте, что копия готова.

Этот стандарт связывает два разных этапа работы:

```text
Product Map + реестр продукта + трассировка
  -> решение владельца о продолжении
  -> Product Owner: story, ценность, границы и DoD
  -> Business Analyst: User Story Map, slices, stories и критерии приёмки
  -> Delivery PM / Orchestrator: план исполнения
```

**Product Map не заменяет User Story Map и не является backlog.** Она отвечает,
что за продукт проектируется, для кого, где его ядро, путь, возможности, границы
и неизвестное. USM появляется только после решения владельца и переводит
принятую часть продукта в последовательность поставки.

## 1. Правило копии

- Мастер-шаблон никогда не редактируется под конкретный продукт.
- Если Google Sheets доступен, оркестратор до начала проектировочного прогона
  создаёт отдельную проектную копию и записывает её URL в `MANIFEST.md`.
- Название копии: `<продукт> — Product Map + USM — <YYYY-MM-DD>`.
- Все роли работают только в проектной копии и не меняют структуру вкладок,
  обязательные поля, значения статусов и схему ID без решения владельца Dream Team.
- Если Google Sheets недоступен, прогон продолжается в канонических Markdown-файлах,
  а `MANIFEST.md` честно фиксирует отсутствие проектной копии.
- Канонический проверенный снимок Product Map остаётся в
  `docs/product-design/<run-id>/PRODUCT-MAP.md` и фиксируется commit-ом. Таблица —
  рабочее совместное представление, а не замена версионируемого снимка.

## 2. Обязательные вкладки и гейт

| Вкладка | Когда заполняется | Владелец содержания | Назначение |
|---|---|---|---|
| `Product Map` | до owner gate | `product-architect` | Читаемый владельцем образ продукта, обзор путей, ядро, решения, пробелы и срезы |
| `Реестр продукта` | до owner gate; блок `SLICE` — после PO | `product-architect`; затем `business-analyst` только для `SLICE` | Единый источник `CORE / JRN / STEP / CAP`, связей шаг–возможность и принятых срезов |
| `Трассировка` | параллельно первым двум | `product-architect` | Связь сущностей с источниками, решениями и подробными файлами |
| `USM` | только после решения владельца и передачи PO -> BA | `business-analyst` | Backbone, delivery slices и user stories принятого scope |

Логический порядок вкладок в мастере и проектной копии:
`Product Map` → `Реестр продукта` → `Трассировка` → `USM`.

До owner gate вкладка `USM` остаётся в состоянии `GATED — решение владельца не
получено`. Архитектор и reviewer не заполняют её «на будущее». Решение владельца
`продолжить в продуктовую разработку` закрывает проектировочный прогон, но не
снимает обязательную цепочку PO -> BA -> Delivery PM / Orchestrator.
После `PASS` Product Map, блоки `CORE / JRN / STEP / CAP / LINK` реестра и
трассировка считаются проверенным снимком. BA изменяет `USM` и добавляет только
принятые `SLICE` в специально отведённый блок `Реестра продукта`. Любая другая
содержательная правка первых трёх вкладок требует нового проектировочного прогона,
нового `PRODUCT-MAP.md` и повторного reviewer-гейта.

## 3. Сущности и стабильные ID

| Префикс | Сущность | Где живёт | Смысл |
|---|---|---|---|
| `CORE` | Product core | `Реестр продукта` | Ядро или самостоятельная область продукта в принятой границе |
| `JRN` | Journey | `Реестр продукта` | Сквозной пользовательский путь для конкретной роли и результата |
| `STEP` | Journey step | `Реестр продукта` | Один независимо задаваемый, изменяемый, проверяемый или отменяемый смысл |
| `CAP` | Capability | `Реестр продукта` | Возможность продукта, принадлежащая блоку ядра и поддерживающая один или несколько шагов |
| `LINK` | Step–capability link | `Реестр продукта` | Явная связь many-to-many между шагом пути и возможностью |
| `TRC` | Trace record | `Трассировка` | Связь сущности с фактом, решением, гипотезой, вопросом или подробным файлом |
| `SLICE` | Delivery slice | `Реестр продукта` + `USM` | Принятый PO проверяемый вертикальный срез поставки с пользовательским результатом |
| `US` | User story | `USM` | История пользователя внутри принятого slice |

Формат ID: `<PREFIX>-NNN`, например `STEP-004`. ID создаётся один раз и не
переиспользуется для другого смысла. Переименование текста не меняет ID; удаление
помечается статусом, а не освобождает номер.

Обязательная цепочка связей:

```text
JRN -> STEP <-> LINK <-> CAP -> CORE
          \                /
           +-> SLICE -> US

TRC -> любая из сущностей выше
```

Одна сущность может иметь несколько связей, но каждая связь указывается явным ID.
Видимая владельцу карта остаётся написанной человеческим языком: ID служат для
связности таблицы и не заменяют названия.

## 4. Минимальные поля вкладок

### `Product Map`

Верхний блок: название продукта, пользователь, контекст, главный результат,
принцип продукта и граница. Ниже — обзор путей, живой вид выбранного пути,
области ядра, решения владельца, пробелы и вертикальные срезы.

`Product Map` показывает человеческий смысл. Стабильные ID создаются в
`Реестре продукта`, а формулы собирают из него обзор путей и выбранный backbone.

| Поле шага | Требование |
|---|---|
| Этап / шаг | Понятное человеку название; один независимый смысл |
| Результат шага | Что стало истиной для пользователя |
| Главный участник | Роль, выполняющая действие |
| Действие человека | Наблюдаемое действие пользователя |
| Возможность продукта | Что продукт обеспечивает для действия |
| Правило / ограничение | Условие допустимости, не подмена действия |
| Статус знания | `факт / решение / интерпретация / гипотеза / открытый вопрос` |
| Граница | `ядро / принятая версия / позже / вне продукта` |
| Подробности | Рабочая ссылка на файл узла или решение |

### `Реестр продукта`

Обязательные блоки:

- `CORE`: ID, название блока, координата Product Map, статус знания, граница,
  `TRC-ID`, подробности;
- `JRN`: ID, название пути, пользователь/контекст, вход, итоговый результат,
  статус покрытия, граница, открытый вопрос и подробности;
- `CAP`: ID, `CORE-ID`, название, пользовательский результат, зависимости,
  продуктовый вопрос, статус знания, граница, `TRC-ID` и подробности;
- `STEP`: ID, `JRN-ID`, отдельный числовой порядок, этап, результат, участник,
  действие человека, возможность, правило, статус, граница, `TRC-ID`, подробности;
- `LINK`: `LINK-ID`, `STEP-ID`, `CAP-ID`, тип связи;
- `SLICE`: `SLICE-ID`, проверяемый результат, граница, решение владельца, статус,
  `JRN-ID` и диапазон `STEP-ID`. До PO этот блок остаётся пустым.

### `Трассировка`

Обязательные поля: `TRC-ID`, утверждение или решение, связанные ID, тип знания,
источник, точная координата или цитата, решение владельца, место на Product Map,
подробный файл, проверивший и дата проверки. Служебная трассировка не дублируется
вручную на основной карте.

### `USM`

Обязательные поля: выбранный путь и автоматически вычисляемый `JRN-ID`,
`STEP-ID`, `CAP-ID`, автоматически вычисляемый `CORE-ID`, `SLICE-ID`, `US-ID`,
тип сценария, роль, story, бизнес-правило, Given / When / Then, статус и `TRC-ID`.
Автоматический контроль подтверждает, что история относится к выбранному пути;
ниже показывается покрытие шагов, возможностей и блоков ядра историями.

Backbone USM наследует принятые `JRN` и `STEP`; BA не переопределяет образ продукта
и не добавляет новую границу молча. `SLICE` — вертикальный проверяемый результат,
а не технический слой. `US` формулируются из живых сценариев и получают Given / When /
Then в `docs/requirements/`.

## 5. Обязанности ролей

- **`product-architect`** создаёт проектную копию через оркестратора, заполняет
  Product Map, блоки `CORE / JRN / STEP / CAP / LINK` Реестра продукта и
  трассировку, поддерживает `PRODUCT-MAP.md`;
  вкладку USM не заполняет.
- **`product-design-reviewer`** сверяет первые три вкладки с проверяемым commit,
  целостность ID и то, что USM осталась за owner gate. Таблица без соответствующего
  `PRODUCT-MAP.md` не получает `PASS`.
- **Владелец** решает судьбу карты. Только явное решение о продолжении разрешает
  оркестратору передать принятый контур в штатную цепочку.
- **`product-owner`** получает проверенную карту и решение владельца, фиксирует
  story, ценность, принятую границу, приоритет и продуктовый DoD в `TASK.md`, затем
  передаёт их BA. Карта сама по себе не считается PO-решением.
- **`business-analyst`** после PO добавляет принятые `SLICE` только в отведённый
  блок Реестра продукта, заполняет USM в той же проектной копии, создаёт
  версионируемый `docs/requirements/USM.md`, требования, сценарии, Given / When /
  Then и решения, требующие владельца; другие проверенные данные первых трёх
  вкладок не меняет.
- **Delivery PM / Orchestrator** хранит URL проектной копии, обеспечивает гейты,
  не допускает редактирование мастера и начинает план исполнения только после
  приёмки результата BA.

## 6. Проверка перехода в разработку

- [ ] Есть `PASS` независимого reviewer и проверенный `PRODUCT-MAP.md`.
- [ ] Владелец явно решил продолжить продуктовую разработку.
- [ ] PO зафиксировал story, ценность, границы, приоритет и DoD.
- [ ] BA сохранил USM с `SLICE` и `US`, не потеряв связи `JRN` / `STEP` / `CAP`.
- [ ] Для stories есть сценарии, критерии приёмки и источники через `TRC`.
- [ ] Неизвестное не превращено в backlog без решения или явной гипотезы.
- [ ] Только после этого Delivery PM / Orchestrator создал план исполнения и
  контракты стыков.
