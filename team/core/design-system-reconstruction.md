# Реконструкция дизайн-системы из референсов

Когда целевая дизайн-система недоступна (внутренняя, закрытая, «пришлют потом»), а строить
надо сейчас — команда реконструирует её по скринам чужого сервиса и собирает экраны с
предсказуемым результатом. Метод обкатан на проекте **sber-onboarding-prototype** (2026-07-02):
по скринам внутренней ДС Caldera реконструирован гайд и собран экран с пиксельным совпадением.

**Эталон применения** (смотреть как пример): `design-kit/refs/caldera/` (каталог референсов) +
`design-kit/caldera/` (реконструированный гайд) + пиксельный тест `/rm/caldera-leads`
(совпадение ±10px с одного скрина).

## Когда какой режим
- **Система закрытая** (библиотеки нет) → полная реконструкция: токены, кубики, паттерны — всё из скринов.
- **Система открытая** (библиотека доступна) → кубики берём из библиотеки, гайд = правила поверх
  (композиция, отступы, словарь паттернов). Реконструируем только то, чего в библиотеке нет.

## Плейбук (5 шагов, гейты не пропускать)

### Шаг 1. Каталогизация референсов
- **Роль:** general-purpose (дешёвая модель — работа механическая).
- **Вход:** россыпь скринов чужого сервиса.
- **Выход:** `design-kit/refs/<система>/<продукт>/` — имена нормализованы; **md-спека на каждый
  скрин**: тип, что это, элементы, ДОСЛОВНЫЕ лейблы (для поиска), паттерны, маппинг на проект,
  теги. Серии состояний одного экрана — одной спекой. README-индекс + правило пополнения.
  Мусор/непонятное → `_unsorted` с пометкой, не выбрасывать молча.
- **DoD:** любой скрин находится поиском по лейблу; у каждого скрина есть спека; индекс актуален.

### Шаг 2. Метод-проба (гейт стейкхолдера)
- **Роль:** visual-designer.
- **Вход:** один типовой скрин из каталога.
- **Выход:** пиксельная реконструкция ОДНОГО экрана в код (песочница-роут) + сравнение
  бок-о-бок со скрином. Цвета — пипеткой со скрина, шрифт — подбором.
- **DoD (гейт):** стейкхолдер глазами принимает качество метода **ДО масштабирования**.
  Не принял — чиним метод, не плодим экраны.

### Шаг 3. Реконструкция гайда
- **Роль:** design-lead.
- **Вход:** каталог референсов (шаг 1) + принятая проба (шаг 2).
- **Выход:** `design-kit/<система>/tokens.md + components.md + patterns.md`. Только видимое
  на скринах; каждый домысел помечен **«гипотеза, уточнить у владельца ДС»** — список дыр
  копится автоматически и уходит владельцу системы одним вопросом, не по одной.
- **DoD:** в гайде нет немаркированных домыслов; список «уточнить» существует как артефакт.

### Шаг 4. Кубики в коде + витрина-каталог (гейт стейкхолдера)
- **Роль:** visual-designer (строго по гайду шага 3).
- **Вход:** гайд.
- **Выход:** базовые компоненты + страница-витрина, где каждый кубик виден во всех состояниях.
- **DoD (гейт):** стейкхолдер глазами принимает каждый кубик на витрине. Не принят — экраны
  из него не собираем.

### Шаг 5. Сборка экранов из кубиков
- **Роль:** frontend-engineer.
- **Вход:** принятые кубики + спеки экранов.
- **Выход:** экраны, собранные только из принятых кубиков; новых визуальных решений
  «из головы» на этом шаге нет — дыра в кубиках возвращается на шаг 3/4.
- **DoD:** каждый следующий экран быстрее предыдущего.

## Критерии успеха практики
- Первый экран — **≤ дня**; каждый следующий быстрее.
- Расхождение со скрином — только там, где скрин молчит.
- Вместо молчаливых домыслов — растущий список «уточнить у владельца ДС».

## По ролям
- **design-lead** — владеет гайдом (шаг 3), помечает гипотезы, ведёт список «уточнить».
- **visual-designer** — метод-проба (шаг 2) и кубики с витриной (шаг 4), пиксельно по скринам.
- **frontend-engineer** — собирает экраны только из принятых кубиков (шаг 5).
- **Стейкхолдер** — два личных гейта качества: после пробы (шаг 2) и на витрине (шаг 4).
