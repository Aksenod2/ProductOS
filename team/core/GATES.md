# GATES.md — гейты оркестратора

> Канон процесса — в `PROCESS.md`. Этот файл — практический чеклист: перед каждым этапом оркестратор проверяет гейт. Не рекомендация — жёсткое правило.

## 0. Принцип: гейтов мало и фундаментальных

Гейты служат цели (надёжное качество), но **куча гейтов = бюрократия = против цели** —
команда вязнет, делает медленнее, не надёжнее.

- **Новый гейт заводим, только если** он ловит **реальный повторяющийся** провал И **дёшев**
  (лучше машинная grep-проверка, чем суждение).
- **Лучше один сильный принцип, чем десять узких проверок.** Новую проблему сначала пробуем
  закрыть строкой в существующем гейте/роли, а не новым гейтом.
- Мягкое — подсказка, не замок. Заказчик переопределяет (см. §6).

## 1. Главный тест: какую дорожку выбираем

Один вопрос перед любым действием:

> *Меняется ли то, что пользователь может делать?*

| Ответ | Дорожка | Гейты |
|---|---|---|
| **Нет** — правка, баг-фикс, косметика, текст, рефактор без новых пользовательских возможностей | **Лёгкая** | Гейты **пропускаются**. Делай сразу → короткий DIGEST |
| **Да** — новый продукт, новая фича, новый пользовательский флоу | **Полная** | Строгие гейты по таблице ниже |
| **Сомневаюсь** | **Полная** | Перестраховаться дешевле, чем переделывать |

## 2. Гейты наличия артефактов (полная дорожка)

Каждый этап требует артефакт предыдущего этапа. Нет артефакта → этап не запускается.

| Этап | Требует | Где лежит | Кто делает |
|---|---|---|---|
| **BA** | TASK.md (сырая идея) | Папка проекта | Заказчик |
| **PM** | requirements.md | Папка проекта | BA |
| **Design Lead** | requirements.md **+** plan.md | Папка проекта | BA + PM |
| **Frontend / Build** | requirements.md **+** plan.md **+** design-spec.md | Папка проекта | BA + PM + Design |
| **QA** | requirements.md (критерии приёмки) **+** готовый артефакт (index.html / код) | Папка проекта | BA + Build |
| **DIGEST** | Результат QA (все AC пройдены) | — | QA |

## 3. Гейты формата (полная дорожка): жёсткие и мягкие

Артефакт есть ≠ пригоден для следующего этапа. Оркестратор проверяет формат перед передачей.

**Жёсткие проверки** — grep, машина, безотказно. Если не пройдено → **блок**, артефакт возвращается автору.

**Мягкие проверки** — требуют суждения. Слабая модель может ложно забраковать хороший артефакт, поэтому это **подсказка оркестратору**, а не замок. Оркестратор задаёт вопрос — но **НЕ автору артефакта**, а его **получателю** (следующей роли по цепочке), и не блокирует.

| Переход | Жёстко (блок) | Мягко (подсказка) |
|---|---|---|
| **BA → PM** | — | Все сценарии в Given/When/Then? Есть матрица «узел × вес» и названы 2–3 несущие оси, каждая — как механизм, а не подпись (`engineering-discipline.md` §9)? |
| **Design → Frontend** | Нет слов «рекомендуется», «на выбор», «можно использовать» в спеке | Все AC покрыты визуально? Есть сводная таблица AC↔компонент? |
| **Frontend → QA** | — | Есть матрица состояний по каждому AC? QA сверяет с BRIEF/замыслом, не только со спекой — есть класс «занижено против несущей конструкции» (`engineering-discipline.md` §9)? |

**Правило для мягких: автор себя не подтверждает.** «Ты уверен?» → «да» от автора — ничего
не стоит: именно так молча прошёл провал основа.рф (все видели, все промолчали). Поэтому
вопрос задаётся **получателю артефакта** — той роли, что будет по нему работать дальше
(BA→PM: спроси PM; Design→Frontend: спроси frontend-engineer; Frontend→QA: спроси QA).
Получатель отвечает одним из двух: «могу работать» → артефакт идёт дальше; «не могу — вот
дыра» → возврат автору с конкретикой. Это дёшево (получатель всё равно читает артефакт
следующим) и убирает самоподтверждение.

## 4. Гейт не пройден — что делать

```
Если артефакта N нет, а этап N+1 запрошен:
1. Остановиться.
2. Запустить предыдущий этап (того агента, который производит недостающий артефакт).
3. Не запускать этап N+1, пока артефакт не появился в папке.

Если жёсткий формат-гейт не пройден:
1. Остановиться.
2. Вернуть артефакт автору с указанием, что именно нарушено.
3. Не передавать дальше, пока не исправлено.

Если мягкая подсказка сработала:
1. Задать вопрос ПОЛУЧАТЕЛЮ артефакта (следующей роли), не автору.
2. Получатель сказал «могу работать» — передавать дальше.
3. Получатель назвал конкретную дыру — вернуть автору с этой конкретикой.
```

**Пример:** запрошен код, но plan.md отсутствует → остановка, запуск PM, ожидание plan.md.

Оркестратор не имеет права «пропустить» этап и вернуться к нему потом. Цепочка последовательна.

## 5. Исключения: что не требует гейта

- Баг-фиксы (поведение восстановлено до описанного в спеке)
- Опечатки, текст, переводы
- Рефакторинг без изменения пользовательского флоу
- Косметика (цвета, отступы в рамках существующей дизайн-системы)
- Добавление комментариев, документации

Всё это — лёгкая дорожка. Делается сразу, все гейты (включая форматные) пропускаются.

## 6. Заказчик переопределяет

Заказчик имеет право сказать «гейты пропускаем, делай сразу». Оркестратор исполняет. Гейты — инструмент оркестратора, не тюрьма.
