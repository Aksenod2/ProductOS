# INSTALL — подключение мастер-команды к новому проекту

## Главное правило: роли не копировать

`ProductOS/team/` — единственный источник поведения Дрим Тим. Полные файлы
`agents/*.md` и `core/*.md` не копируются в продуктовые репозитории: иначе роли
расходятся и перестают обучаться как одна команда.

В проекте остаются только:

- `AGENTS.md` с доменом, стеком, командами, путями и гейтами проекта;
- тонкие launch-адаптеры, если конкретная среда требует свой формат;
- ссылка на мастер ProductOS, а не встроенная копия текста роли.

Для Codex глобальный указатель живёт в `~/.codex/AGENTS.md`: при вызове Дрим Тим
он читает мастер-роль ProductOS и затем проектный `AGENTS.md`. В указателе должен быть
реальный абсолютный путь к клону ProductOS на конкретной машине. Улучшения ролей вносятся
только в мастер-команду, после утверждения заказчиком.

Пошаговый чек-лист. Делается один раз при старте проекта; занимает ~1-2 часа
вдумчивой работы. Не пропускать шаги «потом доделаю» — именно «потом» на OCS
превращалось в боль (release-qa появился ПОСЛЕ провального переноса на прод,
а не до).

## Шаг 0. Развернуть проектный рабочий контур

Сначала прочитать `core/PROJECT-WORKSPACE.md`. Dream Team остаётся мастер-компонентом в
ProductOS, а в продуктовый репозиторий устанавливается только стандартный контур исполнения:
`PROJECT.md`, `docs/epics/`, шаблоны эпика, места для audit/security/research/journal и
`docs/DEBTS.md`.

В проект также подключается `scripts/validate-epic-contracts.sh` (копией или тонким
адаптером): он проверяет статический формат `MANIFEST.md` перед запуском полной дорожки. Это
не заменяет смысловую приёмку получателем.

Перед созданием файлов провести инвентаризацию существующего репозитория. Ничего не
перезаписывать: для зрелого проекта зафиксировать соответствие его текущих путей стандарту в
`PROJECT.md`, затем добавить только отсутствующие части после подтверждения владельца.

Проверка: по проектным файлам можно ответить «какая задача, какая мастер-роль, какой вход,
что создано, кому передано, кто принял и чем проверено» без обращения к памяти чата.

## Шаг 1. Подключить ядро дисциплины

Определить абсолютный путь к клону, например `DREAM_TEAM_ROOT=/home/user/ProductOS`.
Добавить в проектный `AGENTS.md` ссылку на `$DREAM_TEAM_ROOT/team/` и правило: сначала
читать `core/ORCHESTRATOR.md` + нужную роль, затем проектный контекст. Если среда
поддерживает filesystem-ссылки, допустим symlink; если требует собственный формат,
используется тонкий адаптер без копии тела роли.

Если по ходу проекта родился универсальный урок — предложить изменение мастера
ProductOS. После утверждения правится только мастер; проекты получают обновление
при следующем запуске роли.

## Шаг 2. Выбрать роли под стек проекта

- **Минимальный набор для любого проекта**: product-owner, delivery-pm-orchestrator,
  tech-lead, security-reviewer,
  release-qa + исполнители под стек (frontend-engineer и/или backend-engineer).
- **Фронт+бэк проект**: добавить system-analyst, business-analyst, design-lead,
  frontend-integrator, backend-qa, qa-finalizer, devops-engineer.
- **Крупный бэкенд**: backend-engineer расщепляется на api/auth/db/jobs-инженеров
  (см. примечание в `agents/backend-engineer.md` и оригиналы в OCS).

Проектную специфику заполнить один раз в корневом `AGENTS.md`, не в ролях:
- пути проекта (где экраны, где роуты, где схема БД, где тесты);
- стек и версии (фреймворки, БД, хостинг);
- hot-zone файлы (общие файлы, которые правит только оркестратор / по одному);
- доменные факты (роли пользователей, ключевые сущности, бизнес-ограничения).

Проверка: свежий агент выбранной роли называет мастер-файл ProductOS и корректно
пересказывает ограничения текущего проекта из `AGENTS.md`.

## Шаг 3. Адаптировать хуки (автоматические предохранители)

```
mkdir -p <проект>/.claude/hooks
cp hooks/pre-push-main-gate.sh hooks/pre-push-build-gate.sh hooks/post-build-stamp.sh <проект>/.claude/hooks/
chmod +x <проект>/.claude/hooks/*.sh
```

В скриптах в шапке заменить переменные:
- `{{PROD_BRANCH}}` — защищённая прод-ветка; прямой push в неё запрещается;
- `{{BUILD_CMD_REGEX}}` — regex команды прод-сборки (то, чем собирает CI/хостинг,
  например `pnpm\s+(--filter[= ]|-F[= ])@myapp\/web\s+(run\s+)?build\b`);
- `{{BUILD_CMD_HINT}}` — человекочитаемая команда сборки для сообщения блокировки;
- `{{WATCH_DIR}}` — каталог исходников, правки в котором инвалидируют штамп
  (например `web/src`);
- `{{SKIP_VAR}}` — имя переменной аварийного обхода (например `MYAPP_SKIP_BUILD_GATE`).

Затем зарегистрировать хуки в `.claude/settings.json` проекта — взять фрагмент
из `hooks/settings-hooks-snippet.json` и вставить в секцию `hooks`.

Проверка: попытка `git push origin main` без прогона сборки — блокируется
с понятным сообщением и не проходит даже при сбое PR-инструмента. Рабочая ветка отправляется,
а прод-ветка изменяется только через PR после CI и обязательных verdict-ов.

## Шаг 4. Создать AGENTS.md проекта

Взять `core/AGENTS-template.md`, заменить все плейсхолдеры:
- `{{DREAM_TEAM_ROOT}}` — абсолютный путь к корню клона ProductOS на этой машине;
- `{{DREAM_TEAM_VERSION}}` — текущий тег из `VERSION` и commit мастер-репозитория;
- `{{PROJECT}}` — имя и одно предложение «что это»;
- `{{OWNER_NAME}}` — кто принимает продуктовые решения и итоговый `REVIEW.md`;
- `{{STACK}}` — стек по частям репо;
- `{{PORTS}}` — таблица локальных дев-серверов с закреплёнными портами;
- `{{DEPLOY}}` — куда и как деплоится прод, что значит push в main.

Сохранить разделы шаблона: иерархия источников правды, правило журнала,
правило DEBTS.md, гейт сборки, «спека → реализация».

## Шаг 5. Завести документы прозрачности

```
mkdir -p <проект>/docs/journal
cp stakeholder/journal-template.md <проект>/docs/journal/<область>.md
```

- `docs/journal/<область>.md` — журнал работ простым языком; заводится на каждую
  область, НЕВИДИМУЮ стейкхолдеру (бэкенд, инфра, данные). На OCS это был
  `docs/journal/backend.md`.
- `docs/DEBTS.md` — единственный трекер долгов: таблица
  `ID | Долг | Откуда (дата/инцидент) | Риск | Статус`. Правило: новый долг =
  строка сюда; закрыл = ✅ с датой и коммитом. Не дублировать долги в других md.

## Шаг 6. Выбрать уровень доверия стейкхолдера

Читать `stakeholder/trust-levels.md`. **На новом проекте — всегда СТРОГИЙ**,
даже если команда «та же»: новый проект = новые классы ошибок. Ослабление —
только явным решением стейкхолдера по чек-листу из файла, не дрейфом.

## Шаг 7. Прогнать экзамены

Открыть `evals/EXAMS.md` и прогнать хотя бы блок «Критичные» (помечены ⭐)
разговором с оркестратором/агентами по сценариям. Это проверка, что промпты
и хуки реально работают в новом окружении, а не «скопированы и забыты».

Повторять прогон: после изменения промптов команды и при смене модели.

## Шаг 8. Первым делом на проекте — прод-гейт, не «потом»

Как только появляется прод (или прод-подобный стенд) — поднять E2E реальным
браузером (Playwright) и роль release-qa. Это урок №1 из OCS: всё, что
проверялось только локально, на проде ломалось классами багов, невидимыми
локально.

## Как обновлять подключённую команду

1. В клоне ProductOS выполнить `git pull --ff-only` и прочитать `CHANGELOG.md`.
2. Сверить новую версию в `VERSION` с версией, записанной в проектном `AGENTS.md`.
3. Между эпиками обновить версию проекта и создавать новые манифесты уже с ней.
4. Не переписывать проектный контур автоматически: новые обязательные поля и файлы добавить
   после инвентаризации как явную миграцию.
5. Активный эпик по умолчанию закончить на закреплённой версии. Срочный переход выполнить
   только по `core/UPDATE-POLICY.md` с записью в журнале и повторной валидацией контрактов.
