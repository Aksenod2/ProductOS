# Эпики в репозитории — рабочий процесс ProductOS

Внешнего трекера нет. Для каждого проекта единым источником задач, статуса,
решений и приёмки служит `docs/epics/` в его репозитории.

`docs/epics/` — часть стандартного проектного контура из
`team/core/PROJECT-WORKSPACE.md`. Если команда впервые вошла в проект и контура нет,
оркестратор сначала проводит установку или адаптацию контура, а не создаёт эпик в случайном
месте.

## Единица работы

Одна папка `docs/epics/<slug>/` = один эпик/фича. В ней:

- `TASK.md` — пользовательская история, границы, критерии, текущий статус и блокер;
- `MANIFEST.md` — задачи, участники и контракты стыков;
- `requirements.md` — результат BA;
- `plan.md` — результат Delivery PM / Orchestrator;
- `design-spec.md` — результат дизайна;
- `qa.md` — проверка критериев;
- `REVIEW.md` — понятная страница приёмки для владельца проекта;
- `LOG.md` — короткий индекс журнала;
- `log/YYYY/MM/YYYY-MM-DD.md` — фактические события, решения и передачи.

Документы этапов не создаются пустыми заранее. Наличие файла означает, что этап
выполнен и артефакт готов к следующему гейту.

`MANIFEST.md` создаётся до запуска первой роли полной дорожки. Каждый стык содержит четыре
поля из `core/HANDOFF-CONTRACTS.md`: что передаётся, формат/путь, входная валидация и действие
при ошибке. Для денег, прав, API, кода, миграций и прод-релиза используется жёсткий контракт
с автоматической fail-closed проверкой.

## Статусы

Каноническая цепочка:

```text
бэклог → PO → BA → PM/Orchestrator → дизайн → разработка → QA → на приёмке → готово
```

Из любого активного этапа возможен переход в `заблокировано`. Текущий статус
хранится только в `TASK.md`; каждая смена статуса фиксируется в дневном журнале, а `LOG.md`
указывает текущий файл.

## Цикл оркестратора

1. **Взять.** Создать или открыть папку эпика, проверить user story и критерии,
   поставить статус первого этапа.
2. **Спроектировать стыки.** Для полной дорожки создать `MANIFEST.md`, назначить только
   мастер-роли и описать контракты между задачами. Динамические значения не додумывать.
3. **Провести.** Запускать роли строго по `PROCESS.md` и `GATES.md`. После каждого
   гейта добавить запись в дневной журнал и обновить статус в `TASK.md`.
4. **Сдать.** После полного QA заполнить `REVIEW.md`, поставить `на приёмке` и дать
   владельцу проекта ссылку на запущенную версию и короткие шаги проверки.
5. **Принять.** Только владелец проекта меняет `на приёмке` на `готово`. При возврате
   оркестратор ставит нужный активный этап и фиксирует замечания в логе.
6. **Заблокировать.** Поставить `заблокировано`, записать причину, владельца
   следующего действия и условие разблокировки.

## Формат дневной записи

Записи внутри дневного файла идут по времени. `LOG.md` не разрастается: он содержит только
текущий статус, ссылку на сегодняшний файл и индексы месяцев.

```markdown
## HH:MM TZ — роль / имя

- **Задача / этап:** эпик и текущий этап
- **Исполнитель:** `role_id` мастер-роли
- **Вход:** прочитанные артефакты и версия/коммит
- **Событие:** что сделано или решено
- **Артефакты:** ссылки на документы или код
- **Решение / причина:** почему пошли этим путём
- **Стык:** ссылка на контракт в `MANIFEST.md`
- **Передача:** `role_id` получателя — фактически переданный путь
- **Приёмка получателем:** ожидается / могу работать / не могу — несоответствие контракту
- **Блокеры:** нет / причина и владелец
```

Получатель добавляет отдельную запись о приёмке. Запись автора с формулировкой «готово» не
заменяет подтверждение следующей роли.

## Передача на приёмку

`REVIEW.md` обязан содержать:

- что сделано человеческим языком;
- конкретные шаги «сделай X → должно произойти Y»;
- результат QA по всем критериям;
- красный флаг для данных, денег, безопасности или необратимых действий;
- ссылку на запущенную версию, ветку и коммит.

Нечего дать в «проверь сам» — эпик не готов к приёмке.

## Правила

- Оркестратор не ставит статус `готово` самостоятельно.
- Статус не дублируется в отдельных бэклогах и таблицах.
- Артефакты этапов создаются последовательно по гейтам.
- Критичные риски выносятся владельцу проекта явно.
- Команда предлагает изменения процесса, утверждает владелец мастер-команды.

## Масштабирование

- Один дневной файл на эпик: `log/YYYY/MM/YYYY-MM-DD.md`.
- `log/YYYY/MM/INDEX.md` — ссылки на дни и вехи, без повторения событий.
- Более 500 КБ или 500 записей за день → части `YYYY-MM-DD-01.md`, `-02.md`.
- `docs/epics/INDEX.md` группирует эпики; в одной общей папке миллионы лог-файлов не лежат.
