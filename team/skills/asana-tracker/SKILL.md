# Asana — трекер задач команды ProductOS

Единый трекер. Один проект ProductOS = один проект Asana. Задачи живут здесь, не
в файлах репо. Из проекта команда берёт работу; из штаба супервизор видит ту же
картину — **только смотрит, не раздаёт** (Asana стоит над разделением проект/штаб).

## Константы пространства

- Workspace: `1202208504724920`
- Команда (team): **Bugrov.studio** — `1202208455172085`
- Владелец / заказчик: **Денис** (`670231985430317`). В инструментах `me` = Денис.

## Гранулярность: задача = фича (эпик)

- **Верхняя задача в Asana = фича/эпик.** Это уровень Дениса: он заводит «Фича: X».
  Бэклог проекта — только эпики, без россыпи микрозадач.
- **Декомпозиция — забота команды, не заказчика.** Взяв эпик, команда гонит его по
  полной дорожке `team/core/PROCESS.md` (BA → PM → дизайн → код → QA). Внутренние
  шаги команда кладёт **подзадачами** этого эпика (по одному на этап/роль) — для
  своего трекинга и видимости прогресса. Они свёрнуты под эпиком и бэклог не
  засоряют.
- Мелкая правка/баг (если Денис всё же завёл) = **лёгкая дорожка**, без подзадач.

## Формат задачи — user story (чтобы была самодостаточной)

Каждая задача пишется как user story — тогда команде не надо гадать и она не кружит:

> **Как** [кто: студент / преподаватель], **я хочу** [что], **чтобы** [зачем].
>
> **Готово, когда** (проверяемые пункты — это же «проверь сам»):
> - [сделал X → получил Y]
> - …

Пример (Баланс):
> Как студент, я хочу видеть на «Балансе» сумму и историю пополнений, чтобы понимать,
> сколько у меня денег и за что списали.
> Готово, когда: открыл «Баланс» → вижу сумму; вижу пополнения/списания с датами;
> операций нет → понятное «пока пусто», не белый экран.

Кто пишет: Денис даёт суть, **BA-роль доводит до полной story с критериями** перед стройкой
(полная дорожка). Критерии «Готово, когда» = готовый список «проверь сам» для приёмки.
**Нет критериев — задача не готова к работе** (команда коротко просит их у Дениса, не гадает).

## Связь проект Asana ↔ репозиторий ↔ обсуждение

Источник истины — **`PROJECT.md` (вход проекта)**: в нём указано, где код (репо),
где обсуждение (хранилище) и какой это Asana-проект. Оркестратор открывает проект
по `PROJECT.md`, оттуда знает все три адреса.

Алгоритм связки Asana → код:
1. `get_projects(team=1202208455172085)` → найти Asana-проект по имени.
2. Сопоставить с `PROJECT.md` нужного проекта → взять путь к репо и к обсуждению.
3. Работать в репозитории; контекст/требования читать из хранилища.

Опционально Денис дублирует строку `Репо: <путь>` в описании Asana-проекта (`notes`)
для удобства — тогда её можно прочитать через `get_project(opt_fields="notes")`.
Через API это поле команда не пишет (нет рабочего инструмента) — только читает.

## Секции = этапы (канон, одинаково во всех проектах)

```
Бэклог  →  В работе  →  На ревью  →  Готово
                ↕
          Заблокировано
```

- **Бэклог** — фичи, ещё не взятые в работу.
- **В работе** — команда взяла эпик, идёт по дорожке.
- **На ревью** — сделано, ждёт глаза Дениса (приёмка). Мяч на его стороне.
- **Заблокировано** — работа упёрлась во внешнее (ждём решение/доступ/ответ).
  Команда переводит сюда и пишет комментарием, чем именно заблокирована.
- **Готово** — Денис принял (задача `completed`).

## Цикл агента

1. **Взять.** Из «Бэклог» выбрать эпик (по приоритету/префиксам `[Фаза N]`/`[область]`
   в имени). Переместить в «В работе». При полной дорожке — создать подзадачи по
   этапам (`create_tasks` с `parent` = GID эпика).
2. **Сделать.** В репозитории, строго по `PROCESS.md` и гейтам `GATES.md`. По мере
   прохождения этапов закрывать подзадачи.
3. **Сдать.** Переместить эпик в «На ревью». Оставить **комментарий-приёмку**
   (`add_comment`, формат ниже). Саму задачу НЕ завершать. Если упёрлись во
   внешнее — в «Заблокировано» с комментарием, чем именно.
4. **Приёмка (Денис).** Он завершает эпик → «Готово» (принял) или возвращает в
   «В работе»/«Бэклог» с комментарием (доработка).
5. **Пул закрыт → RETRO** в штаб (`ProductOS/logs/`): что/как/хорошо/плохо +
   предложения в канон.

## Комментарий-приёмка («проверь сам») — обязателен при переводе в «На ревью»

Это бывший DIGEST, теперь по-задачно, прямо в Asana. Человеческим языком:

- **Что сделано** — 1–2 строки, без жаргона.
- **Проверь сам** — конкретные шаги: «сделай X → должно случиться Y». Каждое
  «работает» фальсифицируемо за 30 секунд.
- **🚩 Риск** — если трогали данные/деньги/безопасность/необратимое; иначе «нет».
- **Где смотреть** — ветка/коммит/worktree.

Нечего дать в «проверь сам» → задача не готова, в «На ревью» не переводить.

## Правила

- **Не завершать (complete) задачу самому** — приёмку ставит только Денис. Команда
  доводит до «На приёмке».
- **Критичное флагом, а не молча.** Данные/деньги/auth/необратимое — красный флаг
  в комментарии на глаз Дениса (`PROCESS.md` §6).
- **Не переназначать assignee** без явной нужды.
- Префиксы группировки в именах (`[Фаза N]`, `[область]`) — сохранять.
- Команда **предлагает** улучшения процесса, **утверждает** Денис (`PROCESS.md` §7).

## Инструменты (MCP, грузить через ToolSearch по мере нужды)

| Действие | Инструмент |
|---|---|
| Список проектов команды | `get_projects` (team=…) |
| Секции + notes проекта | `get_project` (`include_sections`, `opt_fields="notes"`) |
| Бэклог / задачи секции | `get_tasks` (project / section) |
| Поиск задач | `search_tasks` |
| Детали задачи перед правкой | `get_task` |
| Создать эпик/подзадачи | `create_tasks` (`parent`, `section_id`) |
| Двигать по секциям / завершать | `update_tasks` (`add_projects:[{project_id, section_id}]`, `completed`) |
| Комментарий-приёмка/прогресс | `add_comment` |
