# Исследование: деградация оркестратора и работа этапами (2026-07-03)

Повод: ретро основа.рф — к концу проекта фейлил оркестратор (0 обещанных чекпоинтов,
самоподтверждение гейтов, 5 правок после «✅» без перепроверки), при том что субагенты
со свежим контекстом работали нормально. Гипотеза стейкхолдера: переполнение контекста.

## Диагноз подтверждён исследованиями

- **Chroma «Context Rot»** (18 frontier-моделей, 2025): качество падает задолго до
  заполнения окна — модель с окном 200K заметно деградирует уже на ~50K токенов.
  https://www.trychroma.com/research/context-rot
- **NoLiMa** (arXiv 2502.05167): на 32K токенов 10 моделей падают ниже 50% от своего
  короткоконтекстного уровня. https://arxiv.org/abs/2502.05167
- **Self-preference bias** (Panickssery et al., NeurIPS 2024): LLM-оценщики распознают
  собственные генерации и систематически завышают им оценки — научное обоснование
  запрета «автор принимает сам себя». https://arxiv.org/abs/2404.13076
- **Anthropic «Effective context engineering»**: у модели конечный «бюджет внимания»;
  контекст надо курировать, а не копить.
  https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

Вывод: оркестратор к концу проекта деградирует **закономерно**. Лечится архитектурой,
а не «просьбами быть внимательнее».

**Рабочий ориентир (решение стейкхолдера): ~1/4 контекстного окна** — как в данных
Chroma (200K-окно деградирует на ~50K). Этап планируется так, чтобы оркестратор
не выходил за четверть окна; дошёл до четверти — закрывай этап передаточной запиской.

## Выбор: этапы со свежим оркестратором VS одна сессия со сжатием

Победили **этапы**. Аргументы первоисточников:

1. Anthropic в своей мультиагентной системе работает фазами: «summarize completed work
   phases and store essential information in external memory before proceeding» + «spawn
   fresh subagents with clean contexts while maintaining continuity through careful handoffs».
   https://www.anthropic.com/engineering/multi-agent-research-system
2. Claude Code best practices прямым текстом: «A clean session with a better prompt almost
   always outperforms a long session with accumulated corrections».
   https://code.claude.com/docs/en/best-practices
3. Context rot: деградация начинается ДО лимита → сжатие «по переполнению» срабатывает
   поздно и выполняется уже деградировавшей моделью, теряя детали молча.
4. Авто-compaction Claude Code теряет старые tool-outputs и детали инструкций без
   предупреждения — подтверждено документацией.
   https://code.claude.com/docs/en/how-claude-code-works.md

Сжатие (/compact с указанием «что сохранять») — только аварийный клапан внутри этапа.

## Анти-паттерны (зафиксировать в каноне)

1. Пересказ вместо артефакта (гнать результаты через контекст оркестратора).
2. Автор проверяет сам себя; «заявил успех» без evidence.
3. Работать до лимита и сжимать в последний момент.
4. Невосстановимое сжатие (без путей к файлам, по которым можно перечитать).
5. Параллельные ПИШУЩИЕ агенты без общего контекста (Cognition: конфликтующие
   неявные решения). Последовательные с чётким контрактом — ок.
6. Расплывчатые постановки субагентам без границ и формата результата.
7. Чекпоинты «на честном слове».

## Что Claude Code умеет штатно (для реализации)

- Субагент = всегда свежий контекст; в оркестратора возвращается только финальное сообщение. ✅
- Stop-hook может заблокировать завершение, пока условие не выполнено (например, нет
  файла-чекпоинта) — механика для «ворот этапа». ✅
- Встроенного session-handoff НЕТ — передаточная записка строится файлами руками. ✅ строим сами
- Workflows не пересекают границы сессий — не для этого случая.
