# Миграция 0.1.0 → 1.0.0

Версия **public beta**. Номер MAJOR нужен по
[RELEASING.md](RELEASING.md): изменены обязательные контракты и порядок работы
ролей. `1.0.0` здесь не обещает зрелой автономной команды.

## Что несовместимо

- Полная дорожка начинается с `PROCESS-BRIEF.md` и независимого
  `process-owner: PASS`, а не с раннего продуктового `MANIFEST.md`.
- Для нового ключевого flow/экрана BA фиксирует фактический `AS-IS.md` до TO-BE.
  `TASK.md`, `AS-IS.md` и требования предшествуют манифесту доставки.
- Новый/существенно изменённый organism/template требует composition concept
  и owner gate даже внутри принятой дизайн-системы. Для сложного нового экрана
  предусмотрены image-варианты, затем работающий concept; картинка не разрешает Build.
- Роли, ранние передачи, provenance и runtime/model routing фиксируются по
  обновлённым шаблонам. Для защитных правил нужны доказательства отрицательного
  прогона, а не только зелёные тесты.

## Как обновиться без переписывания проекта

1. Сохраните выбранные ранее версию и commit мастера. Активный эпик по умолчанию
   заканчивается на них; сам по себе `git pull` не даёт права сменить его правила.
2. Прочитайте [CHANGELOG.md](CHANGELOG.md), [политику обновления](team/core/UPDATE-POLICY.md)
   и [общий вход по карте](team/core/START-HERE.md). Согласованная карта процесса
   определяет маршрут исправлений; миграция не запускает полное проектирование.
3. Между эпиками проведите инвентаризацию проектных инструкций и шаблонов.
   После разрешения владельца добавьте только недостающие поля/документы.
   Не создавайте задним числом фиктивные AS-IS, решения или PASS.
4. Для новой полной дорожки закрепите версию/commit и дату в `PROCESS-BRIEF.md`;
   после BA перенесите ту же версию/commit в `MANIFEST.md`. Запишите фактические
   role/runtime ID, модель и проверенный sandbox. Роли остаются в мастер-клоне.
5. Для срочного перехода внутри эпика получите отдельное решение владельца,
   сохраните старую/новую версии и причину в журнале, заново проверьте открытые
   стыки и изменившиеся гейты. Не переносите старую приёмку на изменённый пакет.
6. Проверьте доступность нужных навыков/инструментов и ограничения среды по
   [INSTALL.md](team/INSTALL.md). Декларации `tools` не доказывают read-only.
   Подключение hooks/skills требует адаптера; этот выпуск ничего не устанавливает.
7. Запустите `bash scripts/test-team.sh` из клона ProductOS и необходимые
   поведенческие экзамены в своей среде. Сам подсчёт файлов/экзаменов не является
   испытанием агентов или личной приёмкой.

При конфликте согласованной карты с новым обязательным правилом укажите
конкретный конфликт владельцу и остановите зависимый узел. Молчаливый обход
гейтов или массовая миграция процессов не входят в обновление.

## Опциональные части и границы

Отдел `product-architect` / `product-design-reviewer` остаётся **opt-in
экспериментом**. Его fixture `projects/kanban-product-design-pilot/` намеренно не
содержит готовой карты или PASS; это не результат успешно пройденного пилота.
Личная Google Sheet автора не распространяется: доступный шаблон v4 даёт
владелец проекта; при недоступности используется документированный Markdown-режим.
Product Map этого отдела не заменяет согласованную карту процесса исправлений.

Порядок публикации мастер-команды описан в RELEASING.md. Публикация не разрешает
автоматически выпуск клиентских правок: личная приёмка результата и разрешение
выпуска в каждом проекте остаются отдельными решениями.
