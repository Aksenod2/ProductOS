# Как выпускать обновления Dream Team

Этот файл — чек-лист владельца мастер-команды. Пользователи читают `CHANGELOG.md` и GitHub
Releases; им не нужно разбираться во внутренней кухне релиза.

## Что обновлять при каждом выпуске

1. Получить явное утверждение изменения канона владельцем мастер-команды.
2. Изменить мастер-файлы, экзамены и машинные проверки одним согласованным набором.
3. Добавить запись в секцию `Unreleased` файла `CHANGELOG.md` человеческим языком:
   что изменилось, кого касается и нужны ли действия в подключённых проектах.
4. Выбрать новую версию по правилу MAJOR/MINOR/PATCH и записать её в `VERSION`.
5. Перенести записи из `Unreleased` в датированный раздел версии.
6. Запустить `bash scripts/test-team.sh` и проверку секретов.
7. Провести изменение через PR и дождаться зелёного CI.
8. Создать Git-тег `vX.Y.Z` и GitHub Release с тем же текстом и разделом «Как обновиться».

## Что обязательно написать в GitHub Release

- что стало лучше или безопаснее;
- какие роли, гейты и шаблоны изменились;
- совместимо ли обновление с текущими эпиками;
- что должен сделать пользователь;
- ссылка на полный `CHANGELOG.md`.

## Несовместимое обновление

Если меняются названия базовых артефактов, смысл роли, обязательные поля контракта или
структура проектного контура, это MAJOR-версия. В релизе обязательна отдельная инструкция
миграции. Проекты не переписываются автоматически.

## После релиза

- проверить страницу GitHub Release и clone-команду из `README.md`;
- убедиться, что тег совпадает с `VERSION`;
- оставить `Unreleased` пустым для следующего цикла;
- сообщить пользователям через GitHub Release; для важных несовместимых изменений — отдельным
  постом или сообщением со ссылкой на инструкцию миграции.
