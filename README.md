# Dream Team / ProductOS

Переносимая мастер-команда из 20 AI-ролей для Codex. Она проводит цифровой продукт по
цепочке Product Owner → Business Analyst → Delivery PM / Orchestrator → дизайн → разработка
→ независимые проверки → приёмка владельцем.

Для сырого замысла нового продукта есть экспериментальный отдел проектирования. Он сам
предлагает контур, ядро и области, на существенных развилках приносит владельцу варианты,
а затем собирает понятную Product Map со ссылками на подробные наработки. Независимый
reviewer проверяет пакет; после показа карты отдел ждёт решения владельца и ничего другого
автоматически не запускает.

Это не один большой промпт и не набор персонажей. В репозитории собраны:

- обязанности и границы мастер-ролей;
- процесс, гейты и правила остановки при нехватке решений;
- проверяемые передачи артефактов между ролями;
- стандартная файловая структура для подключаемого проекта;
- инженерные предохранители и экзамены из реальных провалов.

Проект развивается как **public beta**: канон и рабочий контур уже применялись на реальных
проектах, но подключение пока требует ручной настройки путей и проектных команд.

## Как устроено

Dream Team разделена на два слоя:

1. **Мастер-команда** остаётся в этом репозитории: `team/agents/`, `team/core/`, `team/hooks/`
   и `team/evals/`. Роли не копируются по продуктовым репозиториям.
2. **Проектный контур** создаётся в каждом подключённом продукте: `PROJECT.md`, `AGENTS.md`,
   `docs/epics/`, журналы, артефакты этапов, проверки и `REVIEW.md`.

По файлам проекта можно восстановить, кто в рамках какой задачи что создал, на каком входе,
кому передал, кто принял передачу и чем подтвердил результат.

## Быстрый старт

### 1. Клонируйте ProductOS

```bash
git clone https://github.com/Aksenod2/ProductOS.git
cd ProductOS
export DREAM_TEAM_ROOT="$PWD"
```

`DREAM_TEAM_ROOT` — абсолютный путь к корню клона ProductOS на вашей машине.

### 2. Подключите мастер-команду к Codex

Добавьте в глобальный `~/.codex/AGENTS.md`:

```md
Dream Team хранится в `<DREAM_TEAM_ROOT>/team/`.

Когда пользователь вызывает Dream Team:
1. прочитай `<DREAM_TEAM_ROOT>/team/core/ORCHESTRATOR.md` и релевантные core-файлы;
2. загрузи полную мастер-роль из `<DREAM_TEAM_ROOT>/team/agents/<role>.md`;
3. прочитай `AGENTS.md` текущего продуктового репозитория;
4. не копируй и не изменяй мастер-роли внутри продукта.
```

Замените `<DREAM_TEAM_ROOT>` на реальный абсолютный путь. Переменная shell сама по себе не
подставляется в Markdown-инструкции.

### 3. Подключите конкретный проект

Откройте продуктовый репозиторий в Codex и дайте команду:

> Подключи Dream Team к этому проекту. Сначала прочитай мастер-команду и локальные инструкции.
> Проведи инвентаризацию текущей структуры, покажи конфликты со стандартом и только после
> моего разрешения создай недостающий проектный контур. Роли в проект не копируй.

Команда возьмёт за основу [стандарт проектного контура](team/core/PROJECT-WORKSPACE.md) и
[шаблон проектных инструкций](team/core/AGENTS-template.md). Для существующего проекта она
сначала составит карту соответствий и не будет молча перестраивать файлы.

### 4. Запустите первую задачу

Пример:

> Dream Team, проведи эту задачу по полной дорожке. Сначала Product Owner должен определить
> ценность, границы и критерии готовности. Не запускай дизайн и разработку, пока получатели
> артефактов не примут входы по контрактам. Итог подготовь в REVIEW.md.

После запуска ищите работу команды в `docs/epics/<epic-slug>/` подключённого проекта:

- `TASK.md` — задача, границы и статус;
- `MANIFEST.md` — роли, задачи и контракты передач;
- `requirements.md`, `plan.md`, `design-spec.md`, `technical-spec.md` — артефакты этапов;
- `log/YYYY/MM/YYYY-MM-DD.md` — фактическая история исполнения;
- `qa.md` — проверка критериев приёмки;
- `REVIEW.md` — короткая инструкция владельцу «как проверить самому».

## Что команда блокирует

- реализацию новой возможности без продуктовой постановки и требований;
- домыслы BA или дизайна вместо решения владельца;
- передачу артефакта без входной проверки получателем;
- самоприёмку Delivery PM / Orchestrator;
- двух пишущих агентов в одном checkout;
- прямой push в прод-ветку в обход PR, CI и обязательных вердиктов;
- заявление «готово» только на основании сборки или тестов без продуктового сценария.

Заказчик может явно переопределить процесс, но это решение должно быть зафиксировано.

## Как получать обновления

Стабильные версии публикуются в GitHub Releases и помечаются тегами `vX.Y.Z`. Чтобы получить
последние изменения ветки `main`:

```bash
cd "$DREAM_TEAM_ROOT"
git pull --ff-only
cat VERSION
```

Перед использованием новой версии прочитайте [CHANGELOG.md](CHANGELOG.md). Обновление
мастер-команды не переписывает проектные файлы автоматически. Новый эпик закрепляет новую
версию, а уже идущий по умолчанию заканчивается на той версии, с которой начался.

Если хотите получать уведомления, подпишитесь на **Releases only** на странице репозитория.

## Проверка целостности

```bash
bash scripts/test-team.sh
```

Проверка подтверждает число мастер-ролей и экзаменов, синтаксис скриптов, формат JSON,
положительный и отрицательный сценарии контрактов, fail-closed защиту `main` и отсутствие
локального пути автора в исполняемом каноне. Тот же сценарий запускается в GitHub Actions.

## Честные ограничения текущей версии

- автоматического установщика пока нет: проектный контур адаптируется оркестратором;
- хуки требуют подстановки прод-ветки и команд конкретного проекта;
- машинная проверка подтверждает формат контрактов, но не заменяет профессиональную приёмку;
- качество зависит от модели, доступных инструментов и полноты проектного контекста;
- мастер-команда рассчитана прежде всего на Codex; для другой среды нужен тонкий launch-адаптер.
